## 7. Focused review: `scripts/maf_to_fasta.py`

Read in full together with the helpers it imports from `maf_to_sites.py` (`_assign_code`, `QualityMask`, `read_contig_region`, `iter_maf_blocks`, `choose_sample_record`). Not re-run; the 22 tests in `tests/test_maf_to_fasta.py` pass as part of the 140-test suite above.

**Overall: no correctness bugs found.** I traced the trickiest logic, insertion anchoring in `load_sample_alignment` (`:189-298`), through every boundary case:
- a block starting exactly at `win_end` (the `>` at `:226` is deliberate, so its leading insertion attaches to the last window base);
- blocks starting before the window, where the `idx < 0` path still advances `sample_offset` for both aligned and inserted sample bases;
- block boundaries not counting as evidence that an insertion is absent;
- an insertion conflicting with explicit absence, in either block order.

The tests pin every one of these.

| # | Severity | Finding | Location |
|---|---|---|---|
| 7.1 | Medium (plausible, untested) | Same issue as 2.1: the reference strand is ignored (`ref_pos = ref_record.start`). A `−` reference row would be placed at the wrong positions with no error. Fix both scripts with one check in `choose_sample_record` that raises an error. | `maf_to_fasta.py:229` |
| 7.2 | Medium (unverified magnitude) | A block that overlaps the window is walked one base at a time in Python **from the block start**, not from the window start (`:242-274`). For a 1 kb window inside a multi-Mb AnchorWave block, every column before the window is visited, for every sample.
